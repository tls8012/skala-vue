1차 = 2일차 과제: 일차적인 날씨 로딩 vue파일 만들기
개발의 용의를 위해 전체 컴포넌트를 책임지는 WeatherComposition과 각 카드를 담당하는 WeatherItem으로 나누었습니다.
주어진 과제는 크게 각 날씨의 카드 만들기와, 만들어진 카드들의 검색, 회수 및 표기로 구분할 수 있습니다.

    1. 각 날씨의 카드 만들기.
        각 카드는 동일한 양식으로 내용만 바꾸어 넣게 되기 때문에, 카드 하나를 컴포넌트로 제작해 재사용하는 것이 좋았습니다. 그렇기에 주어진 과제 내용인 도시, 날씨, 온도를 표기하고, 버튼 클릭 시 특수 처리하는 함수를 두었습니다. 이 경우에는 단순 alert만 합니다.
        내용을 받아오는 것은 defineProps로 자세한 내용과, 혹시 모를 추가 내용을 위해 msg란을 두었습니다.
        온도에 따라 표기하는 내용을 변경하기 위해, computed로 전달받은 온도 내용을 처리합니다. 간단한 실습이기에 별도 데이터를 불러오지는 않고, 하드코딩합니다.

    2. 전체 컴포넌트 만들기.
        전체 컴포넌트에는 요구사항이 두 가지가 있습니다.
        회수되는 모든 데이터를 표기할 것, 그리고 검색창으로 입력하는 타자 내용에 따라 실시간으로 검색 결과를 조율할 것.
        이를 위해 검색창의 텍스트 란에는 양방향 연결을 넣어 실시간으로 동기하도록 하였고, computed로 검색 결과를 매 번 확인하도록 했습니다. 데이터 양이 적기 때문에 이러한 간단한 처리로도 기능합니다.
        이렇게 회수된 데이터, 혹은, 입력란이 비어 있다면 전체 데이터를 날씨 카드화해 표기합니다. 편하게 관리하기 위해 최대 3칸만 표기되도록 했으며, 3칸을 넘는 내용은 스크롤로 내릴 수 있도록 했습니다.

3차 = 4일차 과제:
    a. 라우팅 적용: 간단한 여러 주소로 라우팅을 적용합니다. 이번에는 /weather/숫자 꼴로 각 상세 페이지에 진입합니다.
        1. 적용 과정에서 router.push를 쓰기 때문에 직전 실습에서 만든 상태바가 고장납니다. 이를 해결하기 위해서는 여러 방안이 있지만, 이번에는 pinia를 사용해 보도록 합니다. footerCity 전용 store를 생성해, 원래 props/emits로 움직이던 작업을 pinia를 통해 움직이도록 합니다. 이 때, 리셋 기능은 원래의 코드를 굳이 고칠 이유가 없어서, 여전히 emits로 동작합니다.

    b. 추가적인 pinia 적용: 과제는 섭씨-화씨 전환을 요구합니다. 
        2. 구현 방안은 여럿 있겠지만, 전역 상태 관리를 위해 상태만 pinia로 적용, 그리고 모두 함께 사용할 단순 js함수를 별도로 작성합니다. 이유는 매 번 store를 만들 이유가 없는 static한 성질을 가진 함수이기 때문입니다. 이것도 매 번 임포트하기 귀찮아서 방법을 찾다가, globalProperty 라는 것을 발견했습니다. main.js는 어차피 모두 사용하기 때문에, 여기서 작성하면 모든 곳에서 전역 함수로 쓸 수 있는 모양입니다.
        app.globalProperties.$함수명 으로 등록하면 이후 $함수명()으로 호출할 수 있습니다.
    
    c. 실제 날씨 api적용: 우선은 하드코딩한 본인 api키를 사용합니다.
        3. 코드 구현에 있어 위 mockdata의 양식을 최대한 활용하기 위해=코드를 최대한 재사용하기 위해 데이터 양식을 맞췄습니다. 맞추기 위해 axios로 얻은 데이터를 잘 가공하는 내부 함수를 두었습니다.
        비동기 처리가 컴포넌트들을 로딩할 때 문제가 꽤 많았습니다. 로딩하지 않은 null값을 참조하거나 하여 사이트가 깨지게 되었습니다. 이를 해결하기 위해, 첫 로딩 시 로딩 완료 여부를 판정하는 isInit 플래그를 두어, 활성화되지 않았으면 비활성화 창을 보여줍니다. 현재는 모든 도시를 한번에 로딩하는 방식이기 때문에 도시가 60개=api키의 분당 요청 한계를 넘으면 휴식하게 됩니다.
        이후, 실시간 업데이트를 위해 내부적으로 타이머를 두었습니다. 마찬가지로 분당 요청 제한 및 전체 요청 제한 안에 들어오기 위해, 한번에 한 도시만, 일정 시간을 두고 업데이트합니다.

    d. element-plus 적용하기
        4. 간단하게, 화씨-섭씨 변환 버튼과 입력란에 적용해 봅니다.
            4-1. 입력란에 적용하면서 동시에 요구사항인 모든 입력에 대해 실시간 반응하도록 하는 것은 상당히 어려웠습니다. el-plus가 기본적으로 한글 조합을 거의 차단하듯 굴러가서, 엔터키를 누르기 전까지는 검색되지 않았습니다. 이를 수동으로 뜯어내 내부의 input에 직접 이벤트를 붙이는 것으로 해결했습니다.
            4-2. 버튼은 버튼 대신 el-button을 넣으니 정상 동작합니다.
    
    d-1. 기타 외부 api활용
        5. 외부 api로 재밌는 작업을 해 봅니다. 우선 https://api.sunrise-sunset.org/json 에서 각 도시의 해 뜨는 시각과 해 지는 시각을 받아옵니다. 이후 'https://worldtimeapi.org/api/timezone/Etc/UTC' 에서 UTC를 받아온 후, 이를 기반으로 지금이 낮인지, 밤인지, 해 뜨는/지는 중인지를 구분해 카드의 배경색을 바꿉니다.
        5-1. 광주를 한 번 확인하고, footer카드의 선택된 도시가 광주일 때, 로고를 5번 클릭하면 이스터에그 페이지로 이동합니다. https://deckofcardsapi.com/api/ 를 활용합니다.

    f. 예쁘게 만들기.
        6. 이 작업은 코파일럿-gpt 5.5 mini를 사용했습니다. 생각보다 코파일럿의 코딩 성능이 좋지는 않아서 보기보다 예쁘게 작업물이 나오지는 않았습니다. 한동안 싸우다가 적당히 포기하고 타협했습니다.

각 컴포넌트 설명:
    AboutComposition: 서비스 소개 페이지입니다. 간단한 설명과 사용 외부 rest api를 적었습니다.
    BaseDashBoard: 공유되는 컴포넌트 배경 컴포넌트입니다. slot을 활용해 title, content, captio을 받을 수 있게 했습니다.
    ReturnToMain: 다양한 컴포넌트가 메인으로 돌아가기 기능을 요구해서, 별도로 분리했습니다.
    SearchBar: 요구사항 중 하나가 input을 별도로 분리해서 weathercomposition인 부모 컴포넌트에서 직접 슬롯으로 넣는 것이었습니다.
    WeatherComposition: 날씨 카드들이 모인 메인 작업 공간입니다. 
    WeatherItem: 개별 도시의 날씨 정보가 담긴 카드입니다. 이름 컨벤션이 주어지기 전에 제작해서 Item 이 되었습니다. 배경색은 현재 시각과 해가 떠있는 여부를 바탕으로 결정됩니다.
    WeatherDetailComposition: 각 도시의 상세 정보란입니다. 위 weatherItem 클릭 시 이동합니다.
    WeatherFooter: 상세 페이지로 방문했던 마지막 도시를 저장하고 있습니다. 하드코딩된 북한 도시라면 이스터에그가 있습니다.
    FooterFunEvent: 간단한 이스터에그입니다.

각 뷰 설명:
    AboutView, HomeView, NotFoundView, WeatherDetailView: 각 페이지 동작에 필요한 뷰입니다. 각각 서비스 소개, 홈페이지, 도시별 상세 페이지입니다.
    EasterEggView: 이스터에그용 뷰입니다.

각 스토어 설명:
    config: 섭씨-화씨 변환용 스토어입니다.
    counter: 기본 제공된 숫자 세기 스토어입니다. 이스터에그 진입용으로 사용합니다.
    footerCity: footer에 마지막 방문했던 상세 페이지 도시를 저장하는데 사용합니다.
    MockWeatherInfo: api연결 전까지 사용했던 가짜 데이터입니다.
    RealWeatherInfo: api가 연결된 진짜 데이터입니다.
    uiMode: 인공지능이 생성한 pretty mode용 스토어입니다.
